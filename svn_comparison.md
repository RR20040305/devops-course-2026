# Сравнение Git и SVN: ответы на вопросы

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

Разница обусловлена архитектурой хранения данных.

**Git — распределённая система.** Каждый разработчик имеет полную локальную копию всего репозитория вместе со всей историей. Ветка в Git — это просто **указатель (ссылка) на один коммит**, лёгкий файл размером в несколько десятков байт. Создание ветки не копирует файлы и не требует обращения к серверу — это мгновенная операция, выполняемая целиком локально.

**SVN — централизованная система.** Ветка создаётся как **полноценная копия директории внутри репозитория** на центральном сервере. Операция `svn copy` физически дублирует структуру каталогов (хотя SVN и использует механизм «cheap copies» для экономии места, с точки зрения пользователя это всё равно выглядит как копирование). Любое действие с веткой — создание, переключение, слияние — требует **сетевого подключения к серверу**, что делает эти операции медленными и зависимыми от доступности инфраструктуры[reference:0].

**Итог:** в Git ветка — это «ярлык» на коммит (почти бесплатно), в SVN — «папка» на сервере (дорого по времени и ресурсам).

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

**Нет, коммит в SVN невозможен без подключения к центральному серверу.**

SVN — централизованная система: весь репозиторий, включая историю всех версий, хранится **только на сервере**. Рабочая копия на компьютере разработчика содержит лишь текущую версию файлов плюс скрытую папку `.svn` со «слепками» для сравнения. Команда `svn commit` по своей природе является сетевой операцией — она отправляет изменения на сервер, где формируется новая ревизия с глобальным номером[reference:1].

Что **можно** делать без сети: редактировать файлы, запускать `svn diff` (посмотреть локальные изменения), `svn status` (увидеть, какие файлы изменены), `svn revert` (откатить правки до версии из последнего чекаута). Это работает потому, что SVN хранит в `.svn` копии файлов на момент последнего обновления[reference:2].

Но **зафиксировать** изменения — создать коммит — нельзя. Нельзя также посмотреть историю, переключиться на другую ветку или обновить рабочую копию до свежей версии. В Git всё это доступно офлайн, потому что история хранится локально у каждого разработчика.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

Несмотря на доминирование Git, есть сценарии, где SVN остаётся разумным выбором:

1. **Работа с большими бинарными файлами.** SVN передаёт только изменения (дельты) бинарных файлов, тогда как Git хранит полную версию каждого файла. Для проектов с большим количеством бинарных артефактов (дизайн, графика, видео, игровые ассеты) SVN может быть эффективнее по дисковому пространству и скорости передачи[reference:3][reference:4].

2. **Строгий контроль доступа к частям репозитория.** SVN позволяет настраивать права доступа **на уровне отдельных директорий и файлов** (кто и что может читать или изменять). В Git разграничение прав на уровне файлов внутри одного репозитория практически отсутствует — доступ даётся ко всему репозиторию целиком[reference:5].

3. **Централизованное лицензирование и блокировки.** В SVN есть механизм **блокировок** (file locking): разработчик может «заблокировать» файл, чтобы никто другой не мог его редактировать. Это критично для бинарных файлов, которые невозможно осмысленно слить (например, PSD-макеты или CAD-чертежи)[reference:6].

4. **Простые линейные процессы и низкий порог вхождения.** Для небольших команд, работающих по модели «одна ветка — один поток задач», SVN проще в освоении: централизованная модель интуитивно понятна, а операции линейны. Git с его распределённой моделью и сложными сценариями слияния может быть избыточен[reference:7].

5. **Единый репозиторий для множества мелких проектов.** SVN позволяет сделать **частичный чекаут** (checkout) — выгрузить только нужную поддиректорию из огромного репозитория. В Git для этого нужны дополнительные надстройки вроде sparse-checkout, которые не всегда удобны[reference:8].

6. **Совместимость с legacy-инфраструктурой.** В организациях, где годами выстроены процессы вокруг SVN (хуки, CI-интеграции, скрипты деплоя), миграция может быть неоправданно дорогой и рискованной.
