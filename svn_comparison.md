# Сравнение Git и SVN: ответы на вопросы

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

Разница обусловлена архитектурой хранения данных.
**Git — распределённая система.** Каждый разработчик имеет полную локальную копию всего репозитория вместе со всей историей. Ветка в Git — это просто **указатель (ссылка) на один коммит**, лёгкий файл размером в несколько десятков байт. Создание ветки не копирует файлы и не требует обращения к серверу — это мгновенная операция, выполняемая целиком локально.
**SVN — централизованная система.** Ветка создаётся как **полноценная копия директории внутри репозитория** на центральном сервере. Операция `svn copy` физически дублирует структуру каталогов (хотя SVN и использует механизм «cheap copies» для экономии места, с точки зрения пользователя это всё равно выглядит как копирование). Любое действие с веткой — создание, переключение, слияние — требует **сетевого подключения к серверу**, что делает эти операции медленными и зависимыми от доступности инфраструктуры.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

**Нет, коммит в SVN невозможен без подключения к центральному серверу.**
SVN — централизованная система: весь репозиторий, включая историю всех версий, хранится **только на сервере**. Рабочая копия на компьютере разработчика содержит лишь текущую версию файлов плюс скрытую папку `.svn` со «слепками» для сравнения. Команда `svn commit` по своей природе является сетевой операцией — она отправляет изменения на сервер, где формируется новая ревизия с глобальным номером.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

1. **Работа с большими бинарными файлами.** SVN передаёт только изменения (дельты) бинарных файлов, тогда как Git хранит полную версию каждого файла. Для проектов с большим количеством бинарных артефактов (дизайн, графика, видео, игровые ассеты) SVN может быть эффективнее по дисковому пространству и скорости передачи.

2. **Строгий контроль доступа к частям репозитория.** SVN позволяет настраивать права доступа **на уровне отдельных директорий и файлов** (кто и что может читать или изменять). В Git разграничение прав на уровне файлов внутри одного репозитория практически отсутствует — доступ даётся ко всему репозиторию целиком.

3. **Централизованное лицензирование и блокировки.** В SVN есть механизм **блокировок** (file locking): разработчик может «заблокировать» файл, чтобы никто другой не мог его редактировать. Это критично для бинарных файлов, которые невозможно осмысленно слить (например, PSD-макеты или CAD-чертежи).

4. **Простые линейные процессы и низкий порог вхождения.** Для небольших команд, работающих по модели «одна ветка — один поток задач», SVN проще в освоении: централизованная модель интуитивно понятна, а операции линейны. Git с его распределённой моделью и сложными сценариями слияния может быть избыточен.

5. **Единый репозиторий для множества мелких проектов.** SVN позволяет сделать **частичный чекаут** (checkout) — выгрузить только нужную поддиректорию из огромного репозитория. В Git для этого нужны дополнительные надстройки вроде sparse-checkout, которые не всегда удобны.

6. **Совместимость с legacy-инфраструктурой.** В организациях, где годами выстроены процессы вокруг SVN (хуки, CI-интеграции, скрипты деплоя), миграция может быть неоправданно дорогой и рискованной.
